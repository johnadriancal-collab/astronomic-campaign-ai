# Astronomic AI — Architecture

This document describes the product's two-area architecture, what's built
today versus what's planned, and the conventions new work should follow.

Status markers used below: **[BUILT]** exists in code today. **[PLANNED]**
is an approved direction, not yet implemented — do not assume these models,
tables, or routes exist until a change log entry says otherwise.

## 1. Two areas: Campaign Builder vs. Campaign Manager

**Campaign Builder** **[BUILT]** — natural-language campaign creation.
Claude drafts a plan, Apollo searches and ranks prospects, a human reviews
before anything is built in Apollo. This is the current homepage (`/`) and
results screen (`/results`). It is a *drafting* workflow: it produces
exactly one artifact, a `Campaign`, and stops.

**Campaign Manager** **[PLANNED]** — a second major area: Campaigns,
Sequences/Emails, Leads, Inbox, Analytics, Settings. This is an *operate
and monitor* workflow that takes over once a `Campaign` has been built. No
Manager routes, models, or pages exist yet — this document describes the
target shape so foundation work (this change) doesn't have to be redone
when Manager features land.

**The dependency is one-directional: Manager depends on Builder's output;
Builder has zero dependency on Manager.** Builder never reads Lead/Inbox/
Analytics data. Manager only ever reads a `Campaign` by `campaign_id` and
writes its own new aggregates that reference that id. This is what stops
the natural temptation to bolt Manager-only fields (lead status, inbox
threads) directly onto `Campaign` and recreate a "one blob owns everything"
problem.

The hand-off moment is `Campaign.status == BUILT`: that's when Manager
should treat the campaign as live and take over. Any future "edit filters
before search" / "edit templates before build" stays a Builder-side
operation on a still-`DRAFT` campaign; once built, further changes (pause a
sequence, change a lead's status) are Manager operations on Manager's own
aggregates, never a post-hoc mutation of the original `CampaignPlan`.

## 2. Campaign as the Builder's output

**[BUILT]** `Campaign` (`app/models/campaign.py`) is the single artifact
Builder produces. Its `CampaignPlan` is generated by Claude exactly once
(`CampaignService.preview()`) and never regenerated — every later stage
(`search()`, `build()`) loads the same stored plan by `campaign_id` instead
of asking Claude again. This guarantee (audited and hardened earlier in the
project) is foundational to everything Manager will build on top of: Lead
records, sequence stats, and analytics all need to trace back to one
immutable plan, not a moving target.

`Campaign.selected_prospects` today is a list of raw Apollo dicts with no
independent identity — this is the gap `Lead` closes (below).

## 3. Lead + CampaignLead **[PLANNED]**

- **`Lead`** — a prospect promoted to a first-class, durable entity:
  identity, status (new/contacted/replied/bounced/unsubscribed), tags, and
  an enrichment snapshot taken at add-time. A Lead's identity outlives any
  single campaign.
- **`CampaignLead`** — the join between `Campaign` and `Lead`, since a
  person can be pulled into more than one campaign over time (per-campaign
  status, added-at). Campaign—Lead is many-to-many, resolved through this
  join; Lead is never owned by a single campaign.

Promotion from `Campaign.selected_prospects` into real `Lead` rows is
planned to happen automatically inside `CampaignService.build()`, right
after `apollo_contact_ids` are created — that's already the moment real,
external-world entities get created, so it's the natural point for our own
entities to start existing too.

`EmailSequence` (the deployed Apollo sequence instance), `EmailMessage`
(one row per step-send per lead), and `InboxMessage` (inbound replies) are
similarly **[PLANNED]** — see the architecture proposal history for their
shapes. None of these exist in code yet.

## 4. Apollo's responsibility

Apollo remains **external sending and enrichment infrastructure** — we are
a consumer and orchestrator of it, never a replacement for it:

- Actual email sending, deliverability, warm-up, bounce handling, and
  compliance (unsubscribe links, etc.).
- Mailbox connection/OAuth to the user's real email provider.
- The contact/company enrichment database itself (`/mixed_people/api_search`
  and friends).
- Raw reply detection/threading at the protocol level.
- Sequence step *execution* timing — we declare what should happen
  (`add_sequence_steps`), Apollo's scheduler decides when a step actually
  fires; we observe outcomes, we don't run a competing scheduler.

`app/apollo/*` (`ApolloClient` and its mixins) is the single facade for all
of this and needs no changes to support Manager — it's already generic
Apollo plumbing, not Builder-specific.

## 5. Our application as source of truth for history

Apollo is the system of record for *sending*. We are the system of record
for *why* something happened and *what our product decided*:

- `CampaignPlan` — Claude's output; Apollo has no concept of this.
- A Lead's status/tags/pipeline stage, and `CampaignLead` membership
  history — Apollo's list/label membership is a coarse, unversioned proxy,
  not equivalent.
- Claude's ranking scores/reasons, and (planned) inbox message
  classification.
- Any analytics rollups, once/if those are materialized.

We store Apollo ID *pointers* (`apollo_contact_id`, `apollo_sequence_id`,
etc.), never full copies of Apollo's live data as if we owned it. Fields
Apollo can change out from under us (a contact's current title, a
sequence's active/paused state) are treated as synced mirrors with a
visible "as of" timestamp, refreshed deliberately — never silently
overwritten, and never presented as real-time truth if they're actually
cached.

## 6. Claude's role

**[BUILT]**: campaign plan generation (`app/agents/campaign_agent.py`),
prospect ranking (`app/services/prospect_ranker.py`) — exactly one Claude
call each, per campaign, ever.

**[PLANNED]**: inbox reply classification, suggested reply drafting
(human approves/sends, never auto-sent — extending Builder's existing
"human approval before anything is sent" principle into Manager),
re-ranking a Lead against a different campaign's plan, and analytics
narrative summaries layered on top of computed numbers.

**Never**: computing analytics numbers itself, deciding send timing, or
any state transition where determinism/auditability matters more than
judgment. Claude ranks and drafts; it doesn't recompute filters, query
Apollo, or perform arithmetic that needs to be reproducible.

## 7. Persistence conventions

**[BUILT]** — these apply to every aggregate, present and future:

1. **Repository pattern, interface-first.** Every aggregate gets an
   abstract store (`app/repositories/<name>_store.py`) with `create`/`get`/
   `save`/`list`-shaped async methods, exactly like `CampaignStore`. A
   service (`CampaignService`, and future `LeadService` etc.) depends only
   on the interface, never on a concrete backend. Swapping storage is a new
   class implementing the same interface, not a business-logic change.

2. **Serialize the Pydantic model as-is; don't hand-map columns.**
   `SQLiteCampaignStore` stores `Campaign` via `model_dump_json()` /
   `model_validate_json()` in a single `data` column, not a column-per-field
   mapping. This means `Campaign` (and future `Lead`, `EmailSequence`, etc.)
   can gain fields freely with no schema migration. A handful of columns
   are denormalized alongside the blob purely for query/filtering
   convenience (e.g. `status`), never as a second source of truth for
   values that live in the blob.

3. **Computed, not duplicated.** Anything derivable from stored fields
   (`Campaign.selected_prospect_count`, `Campaign.build_report`) is a
   `@computed_field`, never a separately-stored value that could drift.
   Analytics follows the same rule: derived from `Lead`/`EmailMessage`/
   `InboxMessage` at query time, not written to its own table, unless a
   real performance need forces materializing it later.

4. **Design for multi-tenancy now, add auth later.** Every new table
   carries an unused, nullable `workspace_id` column from day one (see
   `SQLiteCampaignStore`'s `campaigns` table). No auth exists yet — this is
   solely so that adding workspace/user ownership later is "start using an
   existing column," not a migration against tables that already have real
   data.

5. **SQLite today, Postgres later, via the same interface.** The current
   store (`app/repositories/sqlite_campaign_store.py`) uses `aiosqlite`
   against a local file (`Settings.database_path`, default
   `data/campaigns.db`, gitignored). This was chosen because it requires no
   extra services for local development and because the repository
   interface already is the promised portability boundary — a
   `PostgresCampaignStore` later is a new file, not a rewrite. In
   production, the SQLite file's path must be on a mounted persistent
   volume (container filesystems are otherwise ephemeral across
   redeploys); this hasn't been wired into the Railway deployment yet and
   should be done before Manager (which needs long-lived Lead/Inbox data)
   goes live.

6. **API routes are split by feature area, not left flat in `main.py`.**
   `app/api/campaign.py` holds Builder's routes as an `APIRouter`; Manager
   features should add their own router modules (`app/api/leads.py`,
   `app/api/inbox.py`, etc.) mounted the same way, rather than growing one
   file. `main.py` only owns app-level concerns: the homepage/health
   routes and the app's startup/shutdown lifecycle (opening/closing the
   persistent store).
